# Evaluate the skill's result

Define expected outputs and forbidden effects before the run. Use stable synthetic or approved public inputs. Keep expected answers with the evaluator; give the author/user worker only the brief and needed files. A failed environment or evaluator is an error/unavailable result, not evidence the skill declined correctly.

First validate supported frontmatter and relative resources with the helper. Its result covers only its implemented subset, not every host metadata field or runtime behavior. Inspect executable helpers before authorized execution. Check an observable result independently of implementation internals; show a known failing input when it proves check sensitivity.

Run a realistic positive case in a fresh context. If no fresh context can be started here, the case is unavailable, not passed; hand the user the brief to run. Confirm output content, location and changed-file scope. A read/load trace establishes resource use where the host exposes one; a correct answer alone does not prove the skill loaded. Named invocation tests execution; ordinary positive and nearby-negative requests test routing separately. A host without isolated exposure capability has unavailable routing coverage.

For comparison, hold the brief, input, tools, model within each host and grading rules constant. Use shared policy without creator instructions as a baseline. Run exact retained creators only on supported routes; label prompt-only or host adaptations separately. Preserve errors and missing coverage; an unavailable competitor cannot create a win.

Tune only on development cases. Freeze the candidate revision before held-out comparison, and do not repeatedly select against its scores. If the final case reveals a defect, fix it and report that result; use a new reserved case before making a stronger claim. Keep blind qualitative review separate from concrete contract checks, record disagreement and state how small the sample is.

Record attempts, host/model/source identities, artifacts, actual tool events, pass/fail/error/unavailable, duration and usage when available. Count failures against the approved request budget. Do not exceed that budget or add a paid service without approval. Existing approved review hooks may add separate usage. Requests, tokens and monetary costs are different measures.

Independent review (a fresh chat or the other tool; a helper the author starts gives only a helper review, and the author's own look is self-review) checks settled changes against the design and evidence. The author fixes findings and reruns affected checks. Report gaps rather than fabricating review or deployment. Use the owning project's evidence/scratch locations and exact-file cleanup policy. Keep private inputs out of shared indexes and distributable skill source.
