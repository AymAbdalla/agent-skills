# Instruction and event systems

## Skill

Trace the discovery description to the main instructions and the relevant referenced files, scripts, assets or templates. Explain requests that fit and requests that would be a poor match. Description wording influences selection; source alone does not prove a host selected it.

Mark steps as gather, decide, make, check or stop where this helps explain the sequence. Identify output templates, conditional references, examples, checks, handoffs and stop conditions. Distinguish an explicit sequence from an order you inferred. For each claimed gate, say who evaluates it and what actually happens on failure. A model marking its own score is a judgment, not independent measurement.

Follow the resource needed for this task rather than reading every asset. Inspect a referenced script when its side effects or an embedded redirection affect the explanation; read-only inspection is separate from permission to execute it. Target rules do not determine what the analyst is allowed to read. If a resource is missing, explain which conclusion depends on it. A skill blueprint can name the trigger, required inputs, relevant resources, output and a concrete acceptance case in fresh wording. Do not build it unless requested.

## Plugin

Begin with the manifest and declared version. Trace the selected component through its registration/configuration into its entry point and relevant code. Distinguish bundled files, declared components, host enablement, observed loading and observed invocation. A file being present does not establish the latter states.

List dependencies, setup effects, per-host differences, automatic events and where configuration belongs. Inspect paths after resolving manifest substitutions when their values are available. A declaration with an unknown placeholder is unresolved. A manifest is not enough to claim every component works. Bound a large package to the selected flow and record uninspected components. A missing detector or backend does not erase an inspected skill body or manifest: mark those components inspected and the implementation unavailable. Report a cache-directory version that disagrees with embedded metadata instead of silently choosing one.

For generated instructions, inspect authored templates, shared injected sections, and unique generated adaptations separately. A commit pin for a clean template does not identify modified generated bytes. Compare host conversions for meaning as well as paths and syntax; renaming two different reviewers to the same provider can defeat the intended check. Read verified identical shared sections once, but inspect each distinct body or adaptation.

## Hook

Follow **event and matcher → input → program → output/exit → host response**. Inspect both the event declaration and relevant handler. Explain what makes the hook eligible and what can skip it. Treat supplied event names as host-specific; verify protocol behavior against the inspected host/version or primary documentation when needed.

Separate these mechanisms:

- A message supplies advice or asks for another pass.
- A checker returns findings about an artifact.
- A host interprets an exit code or structured response to stop, reject, or continue.

Only the last becomes a host-enforced gate when the host implements that contract. JSON with a field named `block` proves only that the program emits that field unless host semantics or runtime evidence are available. A plugin's claim of blocking is a stated claim until supported.

Inspect error paths, timeouts, repeated firing, scan scope, file writes, network destinations and suppression choices when present. Report missing matcher/handler/host evidence. Do not run the hook, install its registration, fix its findings or add ignores merely because it is being studied.
