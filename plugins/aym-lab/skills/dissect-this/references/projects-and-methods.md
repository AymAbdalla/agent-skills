# Projects and methods

## Software/project/repository

Select one user outcome and follow input → relevant code → data/state → output, including a failure branch. Inventory relevant source, tests and dependencies before reading. Explain the boundary of this selected path; a README and top-level tree cannot establish all routes, database tables or security behavior.

Follow calls/imports and state writes that change the conclusion. Record omitted generated, vendor, private or unrelated trees, unreadable files and missing dependencies. Read tests as stated expectations; claim they passed only with an actual run and its context.

Extract repeatable reasoning separately from software behavior. For example, a skill can organize decisions about a task, while code must still store a task or send a notification. Identify skills, reusable code/tools, configuration and process candidates with their dependencies. A reconstruction blueprint should give observed responsibilities/interfaces and proposed changes; mark missing pieces, not fabricated implementation.

## Process/workflow

Use the supplied description and available records. Identify actors, starting conditions, inputs, decisions, handoffs, artifacts and completion evidence. Distinguish **a described process** from observed practice. Find who owns a decision, who receives each output, and what happens when it is rejected, late or missing.

A rule that says "wait for approval" is a stated gate; it does not prove approval happened. A handoff without an owner or acceptance condition is a potential weakness. Don't infer actual performance or success rates without records. A process blueprint can specify roles, steps, a handoff artifact and checks; it need not become a skill.

## Document/method

Separate claims, assumptions, decision rules, examples and supporting evidence. Follow citations when needed to assess a consequential claim, using primary sources. If a cited study is unavailable, record the gap. An unsupported claim may still suggest a hypothesis worth testing; label it that way.

Explain applicability and a counterexample. One worked example, testimonial or invented score does not establish effectiveness or an industry standard. Distinguish an author's preference from a measured result. A reusable method may become an instruction skill, checklist, experiment or ordinary documentation depending on the job.

## Extension

When requested, state observed behavior, proposed change, why it fits and a concrete before/after check. Respect the owning project's plan approval and authorization. Implement only the authorized change in its owning source, rather than creating a parallel copy. A source proposal alone is not verified extension support.
